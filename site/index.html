Zyvor · machine control plane

One stable machine API. Real Windows and Linux behind it.

A control plane for Windows and Linux machines. Portals, CI and automation talk to one REST + CloudEvents contract whether the backend is an in-memory demo, real Windows through dockur on a lab host, Linux cloud images on a KVM host through libvirt, or Windows and Linux VMs on KubeVirt.

Why a machine API

Each row is a problem the README names and the part of Kryton that answers it.

One contract

REST + CloudEvents with OpenAPI at /openapi.yaml, whatever the backend. Pagination with limit and cursor.

Lab to production, same API

Prototype on demo, move to dockur or libvirt, ship on kubevirt. Callers do not change.

Linux next to Windows

Eleven Linux cloud-image templates with cloud-init, SSH keys and checksum-pinned images, fetched against an approved SHA-256.

Stable identity

A UUID that survives a VM moving namespace or being renamed, independent of the provider's own name.

More than YAML

Machines, lifecycle, snapshots, jobs and an SSE event stream over HTTP, instead of raw KubeVirt custom resources.

Credentials auditors can read

API keys stored as SHA-256 digests, TLS, per-caller rate limits (429 / RATE_LIMITED, off by default).

Is this host ready?

krytonctl doctor checks auth, catalog, namespaces, DataSources, snapshot CRDs and StorageClass to snapshot class.

Browser console

Embedded noVNC console with no CDN dependency, Copy RDP, and a dockur catalog of 12 images.

Snapshots on CSI

Create, list, restore and delete through the API, the UI and krytonctl. Not available on the dockur provider.

Four providers, honest status

The README is explicit about what is production-ready. KubeVirt is the GA path; the checklist is in docs/GA.md.

What Kryton is not

Not a Windows installer, activation service or media distributor. Microsoft licensing remains the operator's responsibility. Linux images are fetched by the operator against an approved checksum; Kryton ships none.

Out of GA scope

Multiple krytond replicas (single-writer reconciler, in-process event bus; replicaCount: 1) and live migration of the guest VM.

How it fits

Kryton is split at the provider boundary. Callers see one stable machine API; providers translate it into demo state, dockur compose stacks, libvirt domains or KubeVirt VirtualMachines. On KubeVirt it runs on top of it: the question is whether you build the application layer yourself.

Quickstart

Requires Go 1.27.1+. The local demo uses the demo provider with auth disabled: evaluation only.

git clone https://github.com/zyvorai/zyvor-kryton.git && cd zyvor-kryton
make demo   # http://localhost:8080

Drive it from the CLI:

go run ./cmd/krytonctl list
go run ./cmd/krytonctl create win-dev-01
go run ./cmd/krytonctl doctor

Install the binaries:

make build
sudo install -m755 bin/krytond bin/krytonctl /usr/local/bin/

Deploy to a KVM host over SSH and create a Linux VM on libvirt:

./scripts/deploy-remote.sh <host> <user> --key --apikey --provider libvirt
bin/kryton-image fetch --image ubuntu-24.04 --dir /var/lib/kryton/images --sha256 "$APPROVED_SHA256"
krytonctl create --image ubuntu-24.04 --cpu 2 --memory 2048 --disk 20 --ssh-key ~/.ssh/id_ed25519.pub linux-dev
